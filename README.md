## 线路优化

方案参考 [CFNext](https://github.com/PAICNI/CFNext) 的公开做法：实测优选优先、只保留 Cloudflare 官方网段、下发前做 TLS 握手、速度太低的靠后、保底节点前置、IPv6 默认不占名额、头部轮换避免所有客户端挤在同一个 IP。代码是按当前 cfnew 订阅流程单独写的。

以前内置的 10 个「保底」地址只能完成 TCP 连接，TLS 握手会超时，客户端连上去没有存活节点。地区随机列表里的地址也不在 Cloudflare 网段，不能把订阅流量送回这个 Worker。现在这两类地址都不再当作可用节点。

每次生成订阅时按这个顺序组节点：

1. **测活**：对候选地址发送 TLS ClientHello，必须收到 ServerHello。443 不通时再试 8443。握手失败或超时的地址直接丢掉，不再整份下发。
2. **保底**：握手成功、且延迟低速度高的地址标成「保底」，排在最前。没有速度数据时，用一组实测能完成握手的 Cloudflare 入口地址。
3. **实测优选**：带延迟和速度的优选列表里，低于 1 MB/s 的地址在够用时不占名额。电信 / 联通 / 移动仍可按面板筛选。
4. **地区池**：只拉日本、新加坡、美国的 Cloudflare 地址；选德国时拉德国。不再使用地区随机里的非 Cloudflare 地址。
5. **入口**：订阅域名本身始终占一个节点。优选地址全灭时，客户端仍能连上本机。
6. **兜底**：握手成功的地址少于 8 个时，才从低延迟网段随机补几个，并且同样要握手成功才下发。
7. **裁剪**：默认最多 36 个。IPv6 默认不下发；选「仅备胎」时少量 IPv6 排到末尾；选「等权混合」时和 IPv4 交替。
8. **轮换**：保底和前 8 个优选地址每 5 分钟错开一位。

填写了自定义优选 IP 时，默认只下发这些地址、握手成功的入口地址和本机域名。打开「自定义节点合并默认池」后，才会再并入优选池。

外部列表在内存里保留 30 分钟。过期后先用上一份，再在后台刷新；连续拉取失败时，6 小时内继续用最后一份成功结果。

KV 只保存 TLS 握手通过、且去掉随机补足和域名后的紧凑名单。名单没变不写，10 分钟内不重复写，每个实例每天最多写 24 次。没有握手成功的地址，或只用自定义节点时，不写 KV。订阅响应头 `X-Opt` 带上数量、存活地址数和缓存状态。

面板里的开关在「线路优化」。也可以用环境变量 `OPT`、`OPT_LIMIT`、`OPT_PROBE`、`OPT_BALANCE`、`OPT_ANCHOR`、`OPT_MERGE`、`V6_POLICY`、`OPT_REGION`、`OPT_POOL`。

自动同步只覆盖 `_worker.js`。同步脚本解压后会执行 `node scripts/apply-route-optimizer.mjs`，把这套逻辑重新打进去。补丁对不上新版本时，同步会停住，仓库里仍是上一份已经优化过的代码。
